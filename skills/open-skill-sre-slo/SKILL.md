# SRE：SLO / SLI 与错误预算

## 何时使用

- 用户要定 **SLO**、**SLI**、可用性目标，或问「这个服务达标了没有」
- 用户搜 **错误预算**、**error budget**、**燃烧率**、**burn rate**
- 发版或变更前要判断「还能不能发」「要不要变更冻结」
- 要把告警从「机器阈值」收成「用户能感知的可靠性目标」

**不适用**：单机 CPU、磁盘巡检（走 Linux 巡检）；已经确认的故障止损（走故障应急）。

## 执行规则

1. 先 `read_skill` 阅读本文档，再查已纳管实例的指标、告警和 AI 预测。
2. 没有约定窗口和计算方式时，不报一个精确到小数的达标率。
3. 本技能只给目标和门禁建议，不直接改发布系统或告警阈值。
4. 阈值、静默、冻结变更需用户确认后再落到告警规则或工单。

## 推荐流程

1. **选用户旅程**：先定一个用户能感知的路径（下单、登录、接口、页面），不要先从单机 CPU 起算。
2. **定 SLI**（尽量用已有 Prometheus / 平台指标）：
   - 可用性：成功请求 / 全部有效请求
   - 延迟：在阈值内完成的请求占比（说明分位，如 p99）
   - 正确性：业务成功 / 全部请求（有明确错误码时）
3. **定 SLO**：写出目标、窗口、排除项。例如「滚动 30 天，可用性 ≥ 99.9%」。没有历史时，先用近 7 天做临时目标，并标明「待校准」。
4. **算错误预算**：
   - 预算 = 1 − SLO。99.9% 的 30 天预算约为 43 分钟不可用，或 0.1% 的失败请求。
   - 剩余预算 = 预算 − 窗口内已消耗。
   - 燃烧率：近 1 小时、6 小时消耗速度相对于预算的倍数。1 小时烧掉 2% 以上月预算，视为烧得过快。
5. **给门禁**（需确认后才执行）：
   - 剩余预算充足：变更按正常窗口走。
   - 剩余预算低于 20%，或燃烧率持续偏高：冻结非必要发布，只放行止损和缺陷修复。
   - 预算耗尽：停止功能发布，先恢复 SLI，再复盘告警是不是误报。
6. **接到告警**：多窗口燃烧率告警优先于单点阈值；瞬时毛刺走告警降噪，持续烧预算走故障应急。

## 输出要求

- SLI 定义、数据从哪来、SLO、窗口、排除项
- 剩余错误预算和燃烧率（数据不足要写明）
- 发版建议：可发 / 限制发 / 冻结，以及原因
- 明确「已核对 / 建议 / 尚未改动」
